# A working demo is far from a reliable product

Verified: 4 verbatim quotes from 2 sources

Dimension: Processes (processes)

Evidence: experience

How to measure: Compare the time spent before the first working prototype with the time from prototype to production, and track the production success rate of agent-built features in nines.

A demo that works most of the time is only the first nine of reliability, and each extra nine costs as much as the last. Vibe coding is fine for non-critical work, but deployment, auth, payments and configuration are where most of the work is, so set review standards by risk and keep humans in the loop for anything important.

## Quotes

> I felt like I was 80% done but (foreshadowing...) it was a bit closer to 20%.
>
> [Vibe coding MenuGen](https://karpathy.bearblog.dev/vibe-coding-menugen/)

> Vibe coding menugen was exhilarating and fun escapade as a local demo, but a bit of a painful slog as a deployed, real app.
>
> [Vibe coding MenuGen](https://karpathy.bearblog.dev/vibe-coding-menugen/)

> But if you’re writing actual production-grade code, that property should exist, because any kind of mistake leads to a security vulnerability or something like that.
>
> [Andrej Karpathy — AGI is still a decade away](https://www.dwarkesh.com/p/andrej-karpathy)

> When you get a demo and something works 90% of the time, that’s just the first nine. Then you need the second nine, a third nine, a fourth nine, a fifth nine.
>
> [Andrej Karpathy — AGI is still a decade away](https://www.dwarkesh.com/p/andrej-karpathy)
