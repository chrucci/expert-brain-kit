# Tools

Which coding agents, models and supporting tools a team uses, and how it chooses and combines them.

## Where the experts agree
- Do not staff every task with one model. Let the strongest model plan, design, coordinate and handle hard problems such as debugging and security. Send routine, well-defined work to cheaper or smaller models. Teams that do this keep quality steady and cut cost. ([Addy Osmani: Route work to models by difficulty](../principles/osmani/route-work-to-models-by-difficulty.md), [Steve Yegge: Route work to the cheapest capable model; the strong model designs and reviews](../principles/yegge/route-work-to-the-cheapest-capable-model-the-strong-model-designs-and-reviews.md), [Birgitta Böckeler: Plan with strong models, execute narrow tasks with weaker ones](../principles/bockeler/plan-with-strong-models-execute-narrow-tasks-with-weaker-ones.md), [Anthropic engineering: Match model and effort to scope, checkability and supervision](../principles/anthropic/match-model-and-effort-to-scope-checkability-and-supervision.md))
- Choose agents and models with your own evals, not by reputation. Models are strong in some places and fail oddly in others, and they change often. Keep a fixed set of representative tasks, including ones current models fail at, and rerun it whenever a new model or tool comes out. ([Thoughtworks: Choose a small agent tool set deliberately, by evals and task scope](../principles/thoughtworks/choose-a-small-agent-tool-set-deliberately-by-evals-and-task-scope.md), [Andrej Karpathy: Map a model's jagged capabilities empirically](../principles/karpathy/map-a-model-s-jagged-capabilities-empirically.md), [Steve Yegge: Route work to the cheapest capable model; the strong model designs and reviews](../principles/yegge/route-work-to-the-cheapest-capable-model-the-strong-model-designs-and-reviews.md), [Anthropic engineering: Match model and effort to scope, checkability and supervision](../principles/anthropic/match-model-and-effort-to-scope-checkability-and-supervision.md))
- Supporting tools should be built for agents as well as for people. That means CLIs whose help output teaches an agent how to use them, structural constraints such as typing, module boundaries and structural tests that hold agent output in shape, and production telemetry an agent can query precisely. ([Simon Willison: Build tools agents can learn from their own help](../principles/willison/build-tools-agents-can-learn-from-their-own-help.md), [Birgitta Böckeler: Choose stacks and architecture for harnessability](../principles/bockeler/choose-stacks-and-architecture-for-harnessability.md), [Charity Majors: Keep telemetry wide and high-cardinality](../principles/majors/keep-telemetry-wide-and-high-cardinality.md))

## Where they disagree
- **Should code review go to a cheap model or the strongest one?**
  - Review is routine work. Put code review and CI checks on a small, cheap model and save the big model for hard reasoning. ([Addy Osmani: Route work to models by difficulty](../principles/osmani/route-work-to-models-by-difficulty.md))
  - Review is where the strongest model belongs. It plans and reviews while cheaper models implement, and review needs the highest effort because it is heavy on edge cases. ([Steve Yegge: Route work to the cheapest capable model; the strong model designs and reviews](../principles/yegge/route-work-to-the-cheapest-capable-model-the-strong-model-designs-and-reviews.md), [Anthropic engineering: Match model and effort to scope, checkability and supervision](../principles/anthropic/match-model-and-effort-to-scope-checkability-and-supervision.md))
  - Evidence to settle it: Review the same set of agent-written PRs with a cheap model and a strong model. Seed the set with known defects and track which defects each tier catches and what each costs.
  - Metric: Seeded and escaped defects caught per review dollar, by model tier
- **Should a team pick its tech stack to suit agents, or pick on merit and teach agents the stack?**
  - Pick or reshape the stack so agents can be harnessed and can verify their own work, even if that means a different stack or retrofitting constraints. ([Birgitta Böckeler: Choose stacks and architecture for harnessability](../principles/bockeler/choose-stacks-and-architecture-for-harnessability.md), [Lauren Tan: Pick tools and stack for how well agents can verify with them](../principles/tan/pick-tools-and-stack-for-how-well-agents-can-verify-with-them.md))
  - With good help output, docs and vendor skills, agents handle new or private technology well enough that the stack can be chosen on merit. ([Simon Willison: Build tools agents can learn from their own help](../principles/willison/build-tools-agents-can-learn-from-their-own-help.md))
  - Evidence to settle it: Run the same agent tasks in a typed, tightly bounded codebase and in a loosely structured one, each with and without skills or docs, and compare results.
  - Metric: Agent first-attempt success and rework rate by codebase type, with and without skills

## Measured
- Anthropic compared model tiers and effort levels across task types. Cheaper models did well on tasks that had a clear spec and a way to check the result. Higher effort fixed missed edge cases but did not rescue a wrong approach, and it led the agent to make more assumptions on the human's behalf. Note that this is vendor guidance about its own models. ([Anthropic engineering: Match model and effort to scope, checkability and supervision](../principles/anthropic/match-model-and-effort-to-scope-checkability-and-supervision.md))

## Open hypotheses
- Building agent-facing debugging and verification tools for a service gives an outsized productivity gain. ([Lauren Tan: Pick tools and stack for how well agents can verify with them](../principles/tan/pick-tools-and-stack-for-how-well-agents-can-verify-with-them.md))
  - How to test it: Choose one service. For a few weeks before and after adding agent-facing debugging tools, track how many tasks agents finish without human help and how many PRs ship.
- Wide, structured events let agents diagnose production issues faster than split metrics, logs and traces do. ([Charity Majors: Keep telemetry wide and high-cardinality](../principles/majors/keep-telemetry-wide-and-high-cardinality.md))
  - How to test it: Give agents the same set of past incidents to diagnose, once with wide-event data and once with siloed telemetry. Compare time to isolate the cause and how often new instrumentation was needed.
- A small, deliberate set of agent tools beats a broad toolbox because engineers build mastery instead of switching contexts. ([Thoughtworks: Choose a small agent tool set deliberately, by evals and task scope](../principles/thoughtworks/choose-a-small-agent-tool-set-deliberately-by-evals-and-task-scope.md))
  - How to test it: Count AI tools in active use per engineer and compare that count with cycle time and rework across teams, or before and after a team consolidates its tools.
