# Number of agents

How many agents to run, alone, in parallel or in swarms, and the coordination cost that more agents bring.

## Where the experts agree
- Run agents in parallel only when the work splits into independent slices, such as separate files, services or worktrees with no shared state. On coupled work, parallel agents collide, overwrite each other and leave the human to reconcile the results, so judgement-heavy or tightly coupled work should stay with one agent. ([Kent Beck: Watch for the coordination tax of agent swarms](../principles/beck/watch-for-the-coordination-tax-of-agent-swarms.md), [Addy Osmani: Run parallel agents only on independent work, and only as many as you can review](../principles/osmani/run-parallel-agents-only-on-independent-work-and-only-as-many-as-you-can-review.md), [Anthropic engineering: Scale agents only along independent, narrow seams](../principles/anthropic/scale-agents-only-along-independent-narrow-seams.md), [Thoughtworks: Keep subagent waves small and the orchestrator's context clean](../principles/thoughtworks/keep-subagent-waves-small-and-the-orchestrator-s-context-clean.md))
- Human attention, not agent capacity, limits how many agents to run. Each extra agent adds review, cleanup and tracking work for the person running it, and the signs that you have hit the limit are falling review quality, fatigue, or losing track of work in flight. ([Simon Willison: Human cognitive capacity limits agents per person and team size](../principles/willison/human-cognitive-capacity-limits-agents-per-person-and-team-size.md), [Addy Osmani: Run parallel agents only on independent work, and only as many as you can review](../principles/osmani/run-parallel-agents-only-on-independent-work-and-only-as-many-as-you-can-review.md), [Mitchell Hashimoto: Run one or two agents, not a swarm](../principles/hashimoto/run-one-or-two-agents-not-a-swarm.md), [Steve Yegge: Cap the number of agents at what humans and the fleet can absorb](../principles/yegge/cap-the-number-of-agents-at-what-humans-and-the-fleet-can-absorb.md), [Thoughtworks: Keep subagent waves small and the orchestrator's context clean](../principles/thoughtworks/keep-subagent-waves-small-and-the-orchestrator-s-context-clean.md))
- Subagents earn their place by keeping exploration noise out of the main agent's context and by handing routine work to cheaper models, not by forming large swarms of specialist roles. Keep the roster small, merge tasks or specialists that overlap, and keep waves to a handful of agents. ([Simon Willison: Use subagents to protect context and cut cost, not as role swarms](../principles/willison/use-subagents-to-protect-context-and-cut-cost-not-as-role-swarms.md), [Thoughtworks: Keep subagent waves small and the orchestrator's context clean](../principles/thoughtworks/keep-subagent-waves-small-and-the-orchestrator-s-context-clean.md), [Anthropic engineering: Scale agents only along independent, narrow seams](../principles/anthropic/scale-agents-only-along-independent-narrow-seams.md), [Steve Yegge: Cap the number of agents at what humans and the fleet can absorb](../principles/yegge/cap-the-number-of-agents-at-what-humans-and-the-fleet-can-absorb.md))

## Where they disagree
- **How many concurrent agents should one engineer run?**
  - One or two at most. A second agent is for research or for competing on a hard task, and several agents on one codebase cost more in coordination than they return. ([Mitchell Hashimoto: Run one or two agents, not a swarm](../principles/hashimoto/run-one-or-two-agents-not-a-swarm.md), [Kent Beck: Watch for the coordination tax of agent swarms](../principles/beck/watch-for-the-coordination-tax-of-agent-swarms.md))
  - About three to five on independent slices, stopping when review quality or stamina drops. ([Addy Osmani: Run parallel agents only on independent work, and only as many as you can review](../principles/osmani/run-parallel-agents-only-on-independent-work-and-only-as-many-as-you-can-review.md), [Simon Willison: Human cognitive capacity limits agents per person and team size](../principles/willison/human-cognitive-capacity-limits-agents-per-person-and-team-size.md))
  - A larger fleet behind one coordinator is workable if you add agents one at a time and stop when throughput stops rising or the fleet is overwhelmed. ([Steve Yegge: Cap the number of agents at what humans and the fleet can absorb](../principles/yegge/cap-the-number-of-agents-at-what-humans-and-the-fleet-can-absorb.md))
  - Evidence to settle it: Engineers working on comparable service tickets rotate through periods at one, two, four and more concurrent agents. For each period, record accepted output and the human time spent supervising and cleaning up.
  - Metric: Merged changes per engineer-day that pass full review, against human fix-up time and change failure rate, at each concurrency level.
- **Can coordination between many agents on one repo be engineered away, or should teams avoid it and keep humans sequencing the work?**
  - Build the coordination: dependencies validated before a swarm starts, agents atomically claiming unblocked work, and shared spec-linked plans on a channel kept separate from source control. Parallel agents then need no human dispatcher. ([Steve Yegge: Deterministic machinery dispatches work; models act on judgment](../principles/yegge/deterministic-machinery-dispatches-work-models-act-on-judgment.md), [Thoughtworks: Give parallel agents a deliberate coordination channel](../principles/thoughtworks/give-parallel-agents-a-deliberate-coordination-channel.md))
  - Avoid putting several agents on one codebase. Keep each thread narrow and let humans sequence, merge and close threads, because the coordination tax lands on the human anyway. ([Kent Beck: Watch for the coordination tax of agent swarms](../principles/beck/watch-for-the-coordination-tax-of-agent-swarms.md), [Anthropic engineering: Scale agents only along independent, narrow seams](../principles/anthropic/scale-agents-only-along-independent-narrow-seams.md))
  - Evidence to settle it: On the same repo, run parallel agents once with a deterministic claim-and-dependency system and once with human-sequenced threads. Compare collisions and how much human reconciliation each needs.
  - Metric: Agent collisions or duplicated tasks, plus human reconciliation minutes per delivered change, with and without deterministic dispatch.

## Measured
- Session cost data, broken down by main session, subagent and model, showed real savings when the top model fanned routine coding out to subagents running cheaper, faster models. The same data showed no matching benefit from splitting work across many specialist role agents. ([Simon Willison: Use subagents to protect context and cut cost, not as role swarms](../principles/willison/use-subagents-to-protect-context-and-cut-cost-not-as-role-swarms.md))
- Anthropic's measurements found that agent teams multiply token spend. On coupled work, parallel agents in one checkout edited the same files and collided on shared resources such as ports, while work split along file, benchmark or service boundaries ran in parallel cleanly. ([Anthropic engineering: Scale agents only along independent, narrow seams](../principles/anthropic/scale-agents-only-along-independent-narrow-seams.md))

## Open hypotheses
- No single agent count fits a whole team. Each engineer has their own best number, depending on cognitive style and technical limits. ([Charity Majors: Each engineer finds their own agent count from data](../principles/majors/each-engineer-finds-their-own-agent-count-from-data.md))
  - How to test it: Give each engineer a few weeks at each of several concurrency levels, then compare merged changes, change failure rate and cycle time for each person. Check whether the best level varies widely between engineers or clusters around one number.
- Driving one capable agent directly, as a design partner, produces more and needs less rework than routing the same work through a constraining multi-agent harness. ([Robert C. Martin: Drive one capable agent rather than fencing it in](../principles/unclebob/drive-one-capable-agent-rather-than-fencing-it-in.md))
  - How to test it: Split similar features between a single directly driven agent and a role-pipeline or harness setup. Compare output, rework and human time per feature.
- A dedicated coordination channel outside source control, built on shared spec-linked plans, cuts duplicated agent work and keeps frequent agent pushes from overloading CI. ([Thoughtworks: Give parallel agents a deliberate coordination channel](../principles/thoughtworks/give-parallel-agents-a-deliberate-coordination-channel.md))
  - How to test it: Run parallel agents on one repo with and without a separate plan or claim channel. Track duplicated or blocked tasks and CI queue time as agent push frequency rises.
